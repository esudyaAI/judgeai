## Что означает статус

Все 8 снимков — `unreviewed`; **юридически подтверждённых редакций пока 0**. Официальное происхождение и контрольная сумма не доказывают действие конкретной нормы на конкретную дату. Даты получения/принятия/изменения не подставляются вместо даты вступления в силу.

- Полный текст доступен как справочный источник с происхождением и статусом.
- Поиск нормы на дату возвращает только `verified`-снимки с известным периодом действия конкретной нормы `[effective_from, effective_to)`. До сверки он отвечает 404, а не подставляет «последний» текст.
- Пересекающиеся проверенные версии дают 409 и требуют разбора человеком.
- Связи правил legal_core с конкретными версиями норм предусмотрены таблицей `legal_rule_references`; автоматически при импорте не создаются. Пока 0 подтверждённых связей; существующий движок анализа ещё не переведён на этот справочник.
- Исторические редакции, все изменяющие УК/УПК законы как отдельные акты, полный набор разъяснений ВС и практика КС пока не загружены. Следующая очередь определяется поддерживаемыми проверками, а не обещанием собрать всё законодательство РФ.

## Схема и миграция

`legal_acts` — реквизиты акта; `legal_editions` — неизменяемые исходные байты, хеш, URL, текст и версия парсера; `legal_provisions` — статьи/страницы и периоды действия; `legal_rule_references` — конкретное основание правила.

Ревизия `0003_legal_library` добавляет только новые таблицы/индексы/ограничения от `0002`. Backfill старых дел не нужен. Тест проверяет сохранение существующего дела при downgrade только этой ревизии и обратном upgrade. Downgrade удаляет загруженный правовой корпус — сначала экспорт/резервная копия. Не выполнять downgrade автоматически.

## Повторить импорт

Из корня репозитория в окружении Python с зависимостями проекта:

```bash
python -m src.cli.legal_library prepare --help
python -m src.cli.legal_library import --source /path/to/act.source --manifest /path/to/act.json
```

`prepare` требует явное время получения `--retrieved-at` в ISO 8601 с часовым поясом (например, `2026-10-28T12:00:00+00:00`), исходный файл, найденный официальный URL, реквизиты акта и формат (`pravo-export`, `kremlin`, `pdf`). Он не загружает произвольный URL и не подтверждает редакцию. `import` проверяет размер, SHA-256, происхождение и соответствие индексируемых блоков извлечённому тексту, затем сохраняет один документ транзакционно. Повторный импорт не меняет исходные снимки; изменение индекса/парсера при том же снимке отклоняется и требует явного дальнейшего механизма версионирования извлечения.

На втором полном запуске импорта создано **0** новых снимков; количество блоков сохранилось. API имеет только чтение. Импорт — локальная административная команда, секреты берутся из существующих настроек окружения и не выводятся.

## API

- `GET /api/legal/status` — фактические количества и число проверенных редакций/связей.
- `GET /api/legal/acts` — каталог с ограниченной пагинацией.
- `GET /api/legal/acts/{key}/editions` — снимки и происхождение.
- `GET /api/legal/editions/{id}/provisions?q=...` — поиск по тексту/заголовку в конкретном снимке.
- `GET /api/legal/lookup?act=uk-rf&locator=article.18&on=2026-10-28` — только проверенная норма с известным периодом действия.
- `GET /api/legal/rules`, `GET /api/legal/rules/{key}` — каталог правил проверки legal_core (T15.1) и их основания из `legal_rule_references` с происхождением; статус основания `no_basis` / `unreviewed` / `incomplete` / `verified` / `rejected`, правило без основания не скрывается. Связь заводит только `python -m src.cli.legal_library link-rule --rule <ключ> --act <акт> --edition <id> --locator <article.N> --rationale <текст>` на существующую норму сохранённого снимка (повтор ничего не меняет); делать это после юридической сверки (T23).

Внешняя доступность API не включается этим документом. Первая локальная проверка использует отдельный контейнер и БД; основной кабинет продолжает работать в прежнем окружении.

## Структурированные санкции (T5)

Из статей импортированной редакции УК РФ парсер `src/services/statute_sanction_parser.py` извлекает по каждой части виды наказания (основные и дополнительные) с нижней и верхней границей: сроки — в месяцах, обязательные работы — в часах, штраф — в рублях. Результат хранится в `criminal_article_sanctions` (миграция `0004`) со ссылкой на конкретную статью снимка (`provision_id`), т. е. с URL, SHA-256 и статусом редакции; версия парсера — в каждой строке, новая версия добавляет новое чтение рядом со старым.

- Импорт: `python -m src.cli.criminal_sanctions import --act uk-rf` (идемпотентен).
- API: `GET /api/legal/sanctions?article=158&part=2` — санкции с происхождением.
- Первая загрузка: 537 статей, 406 с санкциями (остальные — Общая часть, утратившие силу и статьи-определения), 4102 альтернативы; «на тот же срок» наследует границы предыдущей альтернативы. Штрафы, кратные сумме взятки, хранятся без числовых границ.
- Выборочно сверены с текстом: ч. 1 ст. 105, ч. 1 ст. 111, ч. 2 ст. 158, ч. 2 ст. 228, ч. 1 ст. 264.1. Это техническое чтение **непроверенной** редакции; в анализе оно всегда помечено источником и статусом.

## Проверки и дальнейшие шаги

Проверяются импорт/повтор/конкурентный импорт, хеши, неизменяемость индекса, ложный источник и выдуманный текст, периоды/конфликты редакций, пагинация, парсинг составных номеров, примечаний и сносок, совпадение миграций с моделями и сохранность старых дел. При реальной загрузке сверены статьи 18 и 228.1 УК, 307 УПК и 49 Конституции с сохранённым источником и хешем; это **4 выборочные проверки**, не сплошная юридическая валидация 1 324 блоков.

Следующий этап: юридическая сверка нужных статей и пунктов, явные периоды действия, ссылки на акты об изменении/вступлении в силу, выделение пунктов из PDF с проверкой надстрочных номеров; затем импорт структурированных санкций T5 и подключение правил/отчётов к проверенным идентификаторам. Не переключать анализ на непроверенный корпус ради видимости заполненной базы.

Технический прогон после исправления двух замечаний независимого ревью: **67 тестов API/источников**, покрытие всего пакета src **82.47%** при пороге 80%, линтер прошёл. Для корректного измерения асинхронного SQLAlchemy включён учёт thread и greenlet, как требует [документация Coverage.py](https://coverage.readthedocs.io/en/latest/config.html#run-concurrency); покрытие не ограничено только новыми файлами. Измеритель — dev-зависимость.

При первой загрузке восьми источников время фиксировалось по завершению скачивания файлов и сохранялось при архивировании. Для последующих загрузок CLI требует явное время: произвольный mtime файла не считается свидетельством получения. Метаданные API не загружают исходные байты и полный текст; это проверено перехватом реальных SQL-запросов.
