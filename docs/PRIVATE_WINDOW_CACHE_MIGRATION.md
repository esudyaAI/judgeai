# Приватный кэш LLM-окон: миграционный контракт

Статусы и результаты проверок — только в TASKS.md. План относится к техническому этапу T9/T17.

## Изменение

Отдельная таблица `private_llm_window_extractions`: `chat_id` с FK на `chats.id ON DELETE CASCADE`, хеш окна, поле/версия промпта, JSON-чтение и время создания. Уникальность `(chat_id, input_hash, field, prompt_version)`. Внутри одного дела чтение переиспользуется; между разными делами, включая разных владельцев, не переиспользуется.

Runner передаёт `chat_id` только после существующей проверки владельца/активной учётной записи. Публичного API к кэшу нет. Удаление дела удаляет новый приватный кэш через FK, не затрагивая другие дела. Обновление модели/преобразования отражается в версии промпта. Исходные документы и результаты анализа не изменяются миграцией.

## Backfill и старые записи

Общая `llm_window_extractions` остаётся без изменений. Её старые записи нельзя надёжно приписать владельцу по хешу, поэтому они не копируются и не используются для приватного анализа. Новая таблица начинает пустой и заполняется по фактическим новым обращениям. Старые записи не удаляются автоматически; их срок хранения/очистку определяет ответственный за данные после резервной копии и проверки происхождения.

## Применение и проверка

Перед рабочей миграцией — согласованный backup всей БД и проверка восстановления в отдельную БД. До завершения T17 и отдельного разрешения рабочая миграция не выполняется. Миграция `0013_private_window_cache` следует актуальному head `0012_chat_pins`.

Тестовый upgrade должен сохранять прежние `users/chats/messages/llm_window_extractions`. Проверки: повтор окна в одном деле, два владельца с одинаковым окном, запрет использовать прежний общий кэш, каскадное удаление только целевого дела и отказ неразрушающего downgrade при наличии новых данных.

## Откат

Предыдущий код совместим с дополнительной таблицей и может быть возвращён без SQL downgrade; новый приватный кэш при этом сохраняется. Для сохранения защиты приватности откат приложения не разрешает обход privacy-gate или включение прежних внешних вызовов.

SQL downgrade удаляет таблицу только если она пустая. Если в ней есть данные, downgrade останавливается с понятной ошибкой: сначала нужен отдельный согласованный архив/перенос, затем проверка и повтор. Автоматически удалять новые приватные записи при откате запрещено. Старый общий кэш и исходные дела не меняются ни upgrade, ни разрешённым downgrade.
